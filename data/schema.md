# Assembly dataset

A dataset is one board. `data/<asm>.js` calls `BoardExplorer.register({...})`
with the object described here. It is generated by `tools/assemble.py` from
three inputs; edit those, not the output.

| File | Owner | Holds |
|---|---|---|
| `.build/<asm>/extracted.json` | `tools/build_data.py` | parts list, procedure steps |
| `data/<asm>.testpoints.json` | **you** | expected voltages and their citations |
| `data/<asm>.reference.json` | **you** | fault codes, rail circuits, part functions |
| `data/<asm>.coords.json` | `tools/build_coords.py` / Author Mode | positions |

---

## Top level

```js
{
  id: 'A18',                    // uppercase, matches the manual
  name: 'Filter/PA Supply PCA',
  pca: '761189',                // Fluke assembly number
  rev: 'H',                     // revision the drawing and photo show
  refs: { locator, parts, supplies[], theory, troubleshooting },
  warnings: [ 'text shown at the top of procedure mode' ],
  fixed: false,                 // true for a board that cannot be removed on its own
                                // (a soldered daughter card, the rear panel); the
                                // instrument-configuration log offers no tick box for it
  overview: { summary, connectors, source },
  layers: [ … ],                // board drawing and photograph
  schematics: [ … ],            // sheets
  rails: { … },                 // supply rails and the circuits behind them
  components: [ … ],
  testpoints: [ … ],
  probePoints: [ … ],           // measurable points that are not test points
  procedures: [ … ],
  faultCodes: [ … ],
  caveats: [ … ],               // source disagreements worth knowing about
  tables: [ … ]                 // reference tables shown verbatim
}
```

## Coordinates

Everything is authored in **board space**: `(0,0)` top-left to `(1,1)`
bottom-right of the board drawing. Positions are fractions, never pixels, so
they survive re-exporting the images at a different resolution.

```js
layers: [
  { id: 'drawing', src: 'assets/a18/drawing.png', transform: 'identity' },
  { id: 'photo',   src: 'assets/a18/photo.jpg',
    transform: { H: [ … 9 numbers … ] },   // board space -> photo image space
    landmarks: [ { src: [x, y], dst: [x, y] } ],  // what H was solved from
    approximate: true }                    // fitted from board edges only
]
```

The drawing *is* board space, so it needs no transform. Any other layer
declares a 3×3 homography mapping board space onto its own normalised image
space, which is why one set of coordinates lands correctly on the drawing, on
the photo, and on the two blended together. `landmarks` is kept alongside `H`
so a person can see and re-solve the correspondences rather than face nine
opaque numbers.

Schematic sheets have their own space, one per sheet:

```js
schematics: [
  { id: 'sh1', title: 'Low-voltage Filter/Regulator', src: '…', figure: '…',
    grid: { cols: ['8','7','6','5','4','3','2','1'], rows: ['D','C','B','A'],
            frame: { x0, y0, x1, y1 } } }   // the inner border of the zone grid
]
```

`frame` lets a zone label like `sh1/C4` be derived from a position, so zones
never have to be typed in and never disagree with the coordinates.

### Marker shape

A position also carries the outline its marker is drawn with. Three exist, and
they are the three the viewer can draw — nothing may be offered that renders as
something else:

| `shape` | Drawn as | Used for |
|---|---|---|
| `rect` | rounded rectangle | the default; the box is the silkscreen designator |
| `circle` | ellipse inscribed in the box | a part whose body is a circle on the drawing |
| `point` | circle of the box's shorter side | test points and probe pads |

**A shape is a claim about the geometry, not a decoration.** The reader places a
marker on the designator's lettering, which is a thin rotated strip beside or
inside the part; an ellipse inscribed in that strip is a sliver of an oval, not
a ring around a capacitor. So `circle` is only correct on a box that is the
*component body* — roughly square and centred on the part — and such a box has
to be measured, which the reader does not do. In practice that means `circle`
appears only on hand-placed positions, and `tools/build_coords.py` rejects a
shape on anything else.

Because board space is normalised per axis, a circle on a 5810 × 3420 drawing is
`w = d/5810`, `h = d/3420` — the two differ, and that is correct. The viewer
converts both back to screen pixels, so it draws a circle.

`tools/detect_round_parts.py` measures these bodies off the locator art and
writes a proposal to paste into the overrides; it is an authoring aid, not a
build step, because the full-resolution drawing it reads is not versioned and
nothing in `data/` may depend on it. It fits rectangles as well as circles —
bridge rectifiers, relays, DIP and SIP packages and connectors are bodies with
straight sides, and a body box is worth having whatever shape it is.

### `fitted`, and what a body box is worth

An overrides entry may carry `"fitted": true`. It records that the geometry was
measured by the detector and then rendered on the drawing and checked by eye,
rather than typed from a pixel grid. **The build ignores it**: every entry in
the overrides is `placement: "verified"` either way, and the app shows all of
them as "Position checked by hand".

It is recorded because the two really are different claims and the distinction
is otherwise lost the moment the proposal file is regenerated. A hand placement
is someone's judgement about where a part is; a fitted one is a measurement
against the artwork that someone agreed with. If a separate provenance tier is
ever wanted, this field is what it would be built from, and adding it is one
line in `build_coords.py` plus a label in `PLACEMENT` in `js/app.js`.

A body box changes what a marker *means* — "the part" rather than "the
designator that names it". Search, the info card, the test log and `onFail`
highlighting all resolve a `ref` and never touch geometry, so none of them
notice; what does change is where the view lands when you focus a part, and
how much of the board a marker covers.

## Components

```js
{
  ref: 'C13', kind: 'cap',
  desc: 'CAP,AL,3300UF,+-20%,50V',       // as printed in the parts list
  function: 'Filters the +17 SR supply', // what it does, when known
  fluke: '782458', mfrCode: '62643', mfrPart: 'KME50VN332M30X30LLV',
  qty: 4, esd: true,
  asBuilt: { desc, fluke, mfrCode, mfrPart, src: 'Rev 9 (as built)' },
  board: { x, y, w, h, shape },          // shape: 'rect' | 'circle' | 'point'
  sch: [ { sheet: 'sh1', x, y, w, h, zone: 'C6' } ],
  verified: true, schVerified: true,
  placement: 'verified' | 'agreed' | 'ambiguous' | 'single' | 'collision',
  notOnDrawing: true                     // no silkscreen designator exists
}
```

`kind` drives the marker colour and the type legend: `cap`, `res`, `diode`,
`zener`, `transistor`, `ic`, `resnet`, `fuse`, `jumper`, `relay`, `switch`,
`thermistor`, `varistor`, `connector`, `mech`, `part`, and the families A7,
A10 and A17 added — `inductor`, `transformer`, `crystal`, `socket`, `wire`.

`asBuilt` appears only where the two parts lists disagree, which happens where
the board was revised. The main fields carry the later part; `asBuilt` carries
what this revision was built with.

`placement` records how the position was arrived at, and the app says so rather
than presenting every marker as equally trustworthy.

## Test points

A test point is both a parts-list line and an expectation. Three forms of
expectation exist because the manuals use all three:

```js
{ nominal: 27, tolerance: 8 }        // 27 V ±8 V
{ nominal: 565, tolerancePct: 10 }   // +565 V ±10 %
{ nominal: 0, maxAbs: 1.0 }          // "less than 1.0 V"
```

```js
{
  ref: 'TP10', signal: '+17 SR', rail: '17S', kind: 'wire-loop',
  refPoint: 'TP12',                  // where the meter's low lead goes
  nominal: 27, tolerance: 8, unit: 'V',
  rippleMaxPP: 3, ratedOutput: '1.3 A', regulated: false,
  condition: 'Power on, standby',
  source: 'Table 2-8',               // required: every value cites its origin
  isReturn: false,                   // a return carries no expectation
  noPublishedValue: true,            // the manuals tabulate none (logic lines)
  notInParts: true,                  // real probe target with no parts-list line
  currentLimit: '2 A',
  conflict: '…',                     // where two sources disagree, and which won
  hazard: 'HIGH VOLTAGE',
  inferred: true,                    // value not stated outright in the manual
  onFail: ['CR8','CR10'],
  board: {…}, sch: […]
}
```

Where a point has no single correct reading — the ±PA rails depend on which
mode the supply is jumpered into — it carries `states` instead, and each state
is a complete expectation with its own setup and citation:

```js
states: [
  { label: 'Standby (supply off)', nominal: 0, maxAbs: 1.0,
    source: '§5-23 step 6', onFail: ['Q207'] },
  { label: '+180 V mode', nominal: 190, tolerancePct: 10,
    setup: 'Jumper TP207 to PACOM (TP203)', source: '§5-23 step 7',
    onFail: ['U201','Q203','Q206'] }
]
```

Three fields exist because the manuals are imperfect rather than because the
board is. `noPublishedValue` marks a point the manuals never tabulate — A17's
TP51–TP65 are logic lines — and is what distinguishes that from a value someone
forgot to enter. `notInParts` marks a probe target with no parts-list line: 24 of
A17's 33 test points are plated eyelets in the board rather than a purchased
part. `conflict` records a disagreement between sources and which one the entry
follows, so the decision is visible instead of buried.

`probePoints` are the same shape but identified by `id` rather than `ref`, for
measurements the manual calls for at a component pin rather than a test point
("the cathode of VR211", "U201 pin 1").

## Rails, procedures and fault codes

```js
rails: {
  '17S': { label: '+/-17 S supplies', com: 'TP12', color: '#5ec2a8',
           circuit: { rails, rectifier: [], filters: [], fuses: [],
                      regulators: [], note, source } }
}

procedures: [ { id: '5-23', title, source, prereq,
                steps: [ { n, text, refs: ['TP209','CR217'] } ] } ]

faultCodes: [ { code: '3604', title, measure, expected, com, hi,
                verdict,        // which assembly is at fault, per branch
                refs: [], source } ]
```

`verdict` matters more than `expected`: a fault code is only useful if it says
what an in-tolerance reading means as well as an out-of-tolerance one.

## Invariants

`node tools/check_data.js <asm>` enforces these, and fails the build if any
break:

- designators are unique
- every `refPoint` and every `rails[*].com` resolves to a real test point
- a point with a nominal has a tolerance, and cites a source
- every ref named in `onFail`, a procedure step, a fault code or a rail circuit
  exists on the board
- a point marked `isReturn` carries no expected value
- a point that is neither a return nor `noPublishedValue` has one, so a nominal
  cannot go missing by accident; and one marked `noPublishedValue` does not also
  carry a value
- positions lie within `0..1`
- every `sch[].sheet` names a declared sheet
